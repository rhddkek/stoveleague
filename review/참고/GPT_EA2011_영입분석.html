EA2011 영입 시스템
부분 복원 & 스토브리그 적용안

2026-11-07 · 사용자 제공 APK 정적 분석 · 실행 캡처 아님

분석 보고서원작 기능 도식 12장신규 FA 설계 4장

먼저 결론

EA2011에서 가져올 핵심은 선수 선택 → 적은 수의 조건 조정 → 상대의 짧은 반응 → 결과 확인이다. 확인된 원작 기능은 소속 선수 연봉협상, 일괄 계약, 사용자 제안 트레이드, NPC 제안 트레이드, 용병 계약, 1·2·3차 신인 드래프트, 팜 투자, 상점 스카우트다. 여러 구단의 FA 경쟁 시장은 이번 분석에서 확인하지 못했다.

따라서 01~12는 확인한 기능을 설명하는 부분 재구성 도식, 13~16은 스토브리그를 위한 새로운 FA 설계안이다. 원작 화면 전체를 픽셀 단위로 복구한 결과가 아니다. 글꼴·좌표·장식·일부 표시 항목은 대체했으며 선수와 금액은 예시다. 화면 안의 설명 문구 상당수는 분석용 주석이며 실제 원작 문구가 아니다.

이번 작업은 APK 정적 분석이다. 실행 성공·계약 완료 실플레이·게임 저장 검증·현재 스토브리그 코드 반영은 수행하지 않았다.

1. 연봉협상: 가장 확실히 옮길 수 있는 부분

MS_KeyProcMaster_Stove_Money_List는 전체 계약 여부를 검사하고 선수 선택을 설정하며 개별 팝업과 일괄 계약 경로로 나뉜다. 일괄 처리에서 MS_SetAllPlayerContract를 호출한다. 문자열에는 “선수의 연봉 … 을 승낙하시겠습니까?”와 미계약 선수들의 일괄 계약 확인이 있다.

PM_KeyPopupStoveRefusal에서는 두 자리 선택, 내부 금액값 ±10/±1 수정, 0~99 순환이 보인다. 제출 시 MS_StoveMoneyAI에 값을 전달하고 반환값에 따라 다른 결과 팝업을 연다. 요구 연봉, 합의 금액 입력, 제시 조건의 반응, “%d차 거절” 문자열도 존재한다. 이 기능은 버튼만 눌러 자동 계약하는 구조보다 구체적인 흥정 루프를 갖고 있다.

판정 함수에는 선수 유형·기록 필드에 따른 분기, 일부 난수 호출, 거절 횟수와 관련된 필드 갱신이 있다. 일부 분기만 읽고 “요구액의 90%면 항상 수락” 같은 공통 규칙을 만들면 안 된다. 정확한 전체 수식과 각 필드 의미는 미완료다.

우리 게임 적용: 목록에는 이름·역할·현재/요구 연봉·협상 상태만 둔다. 선수를 누르면 요구액과 제안액을 같은 화면에 둔다. 결과는 “보장액 부족”, “기간을 1년 늘려달라”처럼 판정에서 실제 사용한 이유 한 가지를 우선 표시한다. 일괄 계약은 대상 수·총액·계약 후 가용 예산을 먼저 보여주고 확정한다. 자동 처리로 중요한 선수가 사라지는 동작은 별도 확인 없이 실행하지 않는다.

2. 트레이드: 값 비교와 등록 가능 여부를 나누기

사용자 제안은 MS_KeyProcMasterManager_Player_Trade, NPC 제안은 MS_KeyProcMasterManager_NPC_Trade 경로가 있다. 양쪽 목록은 MS_DrawTradeMyTeamPlayer와 MS_DrawTradeTeamPlayer로 분리되어 있다. 화면 선택과 확인 팝업을 지나 MF_TradeAI가 판정하며, 성공 경로에는 MF_RealTrade, 목록 갱신, 저장 호출이 있다.

MF_GetTradeSlot은 양 팀의 타자/투수 수용 검사 함수를 호출한다. MF_GetTradePosition에는 타선·투수 구성 검사 함수 호출이 있다. 판정 경로에는 타자·투수 종합치 계산도 보인다. 따라서 단순히 양쪽 OVR 합만 비교하는 화면으로 축약하면 중요한 조건을 잃는다. “다음 선발 선수는 트레이드 되지 않습니다”, “정규리그 이후에는 트레이드를 하실 수 없습니다”라는 제한 문구가 확인된다.

기존 추가 분석의 NPC 비교 함수는 첫 선수의 종합 차이와 추가 선수 탐색을 구분한다. 일부 후보 경로에 경력 관련 필드 문턱 보정도 있다. 그러나 이것만으로 AI가 장기적으로 균형을 유지하거나 악용을 막는다고 결론내릴 수 없다.

우리 게임 적용: 위쪽은 받을 선수, 아래쪽은 보낼 선수로 고정한다. 가로 화면에서는 좌우 비교를 허용한다. 공통 비교축은 역할·현재 전력·성장 전망·남은 계약·연봉 부담이다. 추가 선수 선택을 닫으면 기존 제안 구성이 유지되어야 한다. 버튼은 “제안” 하나를 중심에 두고 상세정보는 보조로 둔다. 거절하면 상대가 원하는 보강 포지션이나 부족한 가치 한 가지를 알려준다.

승인 검사 순서 제안: 거래 가능 기간 → 양쪽 선수 소유권/중복 → 등록 수와 필수 포지션 → 예산/계약 → 가치·팀 운영 목표 → 최종 교환. 각 실패 사유는 같은 판정 객체에서 UI로 전달한다. 완료 때 소속·등록·계약 부담·기록을 한 번에 갱신하고 저장한다.

3. 외국인 영입: 명단에서 끝나지 않게

MS_KeyProcMaster_Stove_Mercenary_List는 선택과 팝업 경로를 가지며 DT_is2ndPlayerFull을 호출한다. APK에는 계약 확인, 계약 완료, 용병 최대 2명, 2군 로스터 부족 문구가 있다. 숫자 2는 이 게임의 문구이며 현재 현실 리그 규정으로 취급하지 않는다.

우리 게임 적용: 후보 목록 → 기존 선수와 비교 → 계약 조건 → 총비용/등록 점검 → 완료 → 로스터 배치로 연결한다. 별도 영입 수수료가 있다면 연봉과 같은 화면에서 합산해 표시한다. 선수 상세를 닫을 때 필터·정렬·스크롤을 유지한다. 계약 후에는 “선발진 보기”나 “타순에 배치”를 제공한다. 해외 성적·스카우트 신뢰도·적응 위험은 상세 탭에 두고 목록에는 역할과 비용을 우선한다. 이는 신규 설계다.

4. 신인 드래프트와 팜

1차·2차·3차 목록 및 입력 함수가 따로 있다. 원작 안내는 1차에 자기 구단팜, 2·3차에 모든 구단팜을 언급한다. 이것을 현재 KBO의 1~3라운드 지명 방식과 동일시하지 않는다. 후보를 선택하는 화면이 따로 있다는 점과 선수 정보 확인 흐름이 참고 대상이다.

팜 메뉴에는 A~D 선택 및 5/4/3/2×1,000 비용 검사, 부족 자원 표시, 투자 확인이 있다. 후보 생성 함수에는 단계에 따른 분포가 있고, 이전 정적 분석에서는 현재 능력 기준과 잠재력 추첨이 분리된 경로가 확인됐다. 투자는 좋은 신인을 확정 지급하기보다 후보 분포를 바꾸는 장치로 해석할 수 있다. UI 등급과 모든 내부 단계의 최종 매핑은 미확정이다.

우리 게임 적용: 지명 화면 상단에는 현재 순번·내 지명까지 남은 수·부족 포지션을 둔다. 후보마다 현재 수준·성장 전망·관찰 신뢰도를 구분한다. 선택 전 “이번 지명 확정”, 선택 후 “육성 계획 지정”을 이어준다. 드래프트를 기다리는 동안 관심 후보가 다른 팀에 지명되면 짧게 알려준다. 지명은 되돌릴 수 있는 임시 선택과 최종 확정을 구분한다.

5. 상점 스카우트와 코치 영입은 별도 체계

상점 스카우트는 비용을 지불해 영입하는 경로다. BALL 부족, 도전과제 해금, 타자/투수 2군 정원 문구가 있다. “마스터 모드의 기본 소속 선수들은 트레이드와 선수 조합을 통해서만 획득”한다는 안내도 있다. 이 때문에 상점 구매를 모든 선수의 자유계약 시장으로 해석하면 안 된다.

코치에는 이미 계약한 코치 경고와 기존 코치가 자동 삭제된다는 교체 확인 문구가 있다. 원작의 교체 방식을 그대로 가져오기보다, 우리 게임에서는 교체 대상·효과 차이·비용·남은 계약 처리를 먼저 보여주는 편이 이해하기 쉽다. 원작 BALL 상품, 선수 조합, 네트워크 카드 거래는 현실 구단 운영과 성격이 달라 이번 핵심 이식 범위에서 제외한다. 해당 기능이 없는 것으로 단정한 것은 아니다.

6. 우리 FA: 4개 화면으로 끝내는 설계

시장 → 조건 제시 → 선수 답변 → 최종 계약. 이 구조는 EA2011에서 확인한 단순한 협상 단위를 바탕으로 확장한 제안이다. 여러 구단 경쟁, 계약기간, 역할 약속, 마감일은 이 APK에서 복원된 FA 기능이 아니다.

화면항상 보일 정보주 행동
시장포지션·핵심 수준·희망 조건·진행 상태협상
조건선수 요구와 내 제안·총보장액·올해 지급액·가용 예산제안 제출
답변수락/조정/거절·실제 이유·답변 마감수정 또는 유지
확정최종 조건·연도별 부담·등록 가능 여부·변경 전후계약 확정

제안 중, 답변 대기, 수정 요청, 합의, 계약 완료, 철회, 타 구단 계약, 만료를 별도 상태로 저장한다. “합의”는 등록·지출까지 끝난 “완료”와 다르다. 진행 중 표시 개수는 이 상태에서 계산하고 화면별 별도 숫자를 유지하지 않는다.

비용은 최소한 총보장액, 올해 지급액, 영입 시 즉시 비용, 연도별 계약 부담으로 나눈다. 올해 지출 여력과 미래 계약 약정 한도를 각각 검사한다. 연봉×기간을 먼저 전액 차감한 뒤 매년 또 차감하는 이중 정산을 피한다. 리그별 보상·등록 규칙은 게임 설정으로 분리하고 이번 보고서가 현실 규정을 확정하는 자료로 쓰이지 않게 한다.

FA 선택이 단순 최고액만으로 결정되지 않게 하되 이유는 납득 가능해야 한다. 선수 성향에 따라 보장액·기간·역할·우승 가능성의 가중치를 두고, 공개된 희망 조건과 결과 설명이 같은 계산 근거를 사용하도록 한다. 더 적은 돈을 제시한 구단으로 갔다면 실제 결정 요인을 한 줄로 알려준다. 모르는 경쟁 제안 금액을 UI가 전지적으로 공개하지 않는다.

7. 구현 순서와 확인 기준

  1. 거래 상태와 비용부터 통일. 계약 제안·답변·확정을 분리하고 예산/등록 검사를 공유한다. 실패하면 일부만 차감되거나 선수만 이동하지 않아야 한다.
  2. 협상 화면 한 종류로 통일. 재계약·FA·외국인에서 공통 조건 표를 사용하되 해당 거래에 필요한 항목만 노출한다. 원작처럼 선택할 것이 한눈에 보여야 한다.
  3. 트레이드 양측 비교. 선수 선택 과정에서 제안이 초기화되지 않게 하고, 팀별 필요 포지션·경쟁 목표를 판정에 반영한다.
  4. 겨울 진행판. 미계약 핵심 선수·보강 자리·지명·마감일을 4~5줄로 보여준다. 모든 메뉴를 “오늘의 결정” 카드로 쌓지 않는다.
  5. 완료 후 팀 변화. 영입 선수의 예상 역할, 이전 선수 대비 변화, 다음 행동을 짧게 보여준다. 기록은 상세에 남긴다.

확인 기준: 중복 확정 클릭에도 한 번만 계약 / 계약 직전 예산 변경 시 재검사 / 영입 중 다른 팀과 계약한 선수 처리 / 등록 정원 초과 / 제안 철회 후 재개 / 저장 후 답변 상태 유지 / 일괄 계약 대상·총액 일치 / 거래 후 필수 포지션 유지 / 미계약 선수 자동 소멸 방지 / 여러 벤치 선수를 합쳐 스타를 무조건 얻는 악용 방지. 이 항목들은 우리 게임의 검증 제안이며 원작에서 발견한 실행 버그 목록이 아니다.
